# Business Requirements Document — Reporting & Dashboards

## 1. Executive Summary / Business Objective
`CORE_REQUIREMENTS_AND_GAP_ANALYSIS.md` listed the source SRS's Reports & Analytics section (§3.9 — price comparison, cycle-time, dashboards) among the sections judged "genuinely reusable across any vertical." The business objective of this sub-module is visibility, not new business logic: give every stakeholder role a live, at-a-glance answer to the standard ERP inventory questions — what needs attention right now, how much stock is worth, how long are orders sitting open, how fast do suppliers fulfil, what's the cheapest source for a product, and how does spend compare to budget — built entirely as read-only rollups over data the other six sub-modules already capture and persist, with zero new domain entities of its own.

## 2. Stakeholders
- Store/warehouse and procurement staff (Dashboard, Stock Valuation, PO Aging/Cycle-Time — day-to-day operational visibility)
- Procurement/purchasing staff (Price Comparison — sourcing decisions)
- Finance/admin staff (Budget vs. Actual)
- Facilities/asset owners (Asset Depreciation Summary)
- Module administrators (Dashboard, as the one cross-cutting view spanning every other stakeholder's own area)

## 3. Business Rules
| ID | Rule | Rationale |
|---|---|---|
| BR-RPT-1 | The Inventory Dashboard is a single overview screen with eleven directly-defined metrics, not the start of a general "reports module" — every metric is a figure already fully defined by an entity/status shipped elsewhere, chosen specifically because it needed no product-input judgment call. | Decision Log, 2026-09-08 "Inventory Dashboard slice (OC-219)". |
| BR-RPT-2 | Stock Valuation groups by Category only and never sums raw quantity across a category, only distinct product count and total value. | Products in the same category can carry different UOMs (kg, pieces, litres), so a summed quantity would be meaningless; money is always safely summable (Decision Log, 2026-09-09 "Stock Valuation Report slice (OC-221)"). |
| BR-RPT-3 | PO Aging buckets by `poDate` (order date), not `expectedDeliveryDate` — a separate "overdue delivery" view would be a genuinely different report and is not assumed to exist here. | "Aging" in every standard PO aging report means how long an order has been outstanding since it was raised (Decision Log, 2026-09-09 "Purchase Order Aging Report slice (OC-222)"). |
| BR-RPT-4 | PO Aging's "open" status set is deliberately identical to the Dashboard's "Open Purchase Orders" tile definition. | Consistency between the two screens matters more than re-deriving the same judgment call twice (Decision Log, 2026-09-09 "Purchase Order Aging Report slice (OC-222)"). |
| BR-RPT-5 | Asset Depreciation Summary reuses the exact same depreciation formula as the Asset Register (extracted into a shared `AssetDepreciationCalculator`, not reimplemented). | A financial calculation as fiddly as straight-line depreciation drifting into two slightly-different implementations across two screens would be a real, hard-to-notice bug class (Decision Log, 2026-09-09 "Asset Depreciation Summary Report slice (OC-223)"). |
| BR-RPT-6 | Assets missing full depreciation inputs still count toward a category's asset count and purchase-value total, but contribute zero to accumulated depreciation/book value — never silently dropped. | Matches the Asset Register's own existing `depreciationApplicable` flag posture; never fabricates a number the underlying data doesn't support (Decision Log, 2026-09-09 "Asset Depreciation Summary Report slice (OC-223)"). |
| BR-RPT-7 | Price Comparison does no currency conversion — each row shows its own currency as-is. | Matches the module's existing, already-logged posture on multi-currency being informational only everywhere else (`PurchaseOrder`, `VendorProductMapping`) (Decision Log, 2026-09-09 "Price Comparison Report slice (OC-224)"). |
| BR-RPT-8 | Budget vs. Actual groups by Location and sums every currently-active Budget for that location regardless of each budget's own period. | Extends the Dashboard's own already-accepted "over-allocated budgets" simplification rather than inventing a new one; a genuinely period-aware version needs a real answer to what period a deployment's budgeting calendar uses, which is out of reach here (Decision Log, 2026-09-09 "Budget vs. Actual Report slice (OC-225)"). |
| BR-RPT-9 | PO Cycle-Time only counts `COMPLETED` orders, measured from `poDate` to the latest confirmed Goods Receipt's `confirmedAt`; grouped and averaged by supplier, plus a true overall average computed directly across every order (never an average of per-supplier averages). | An order still open, or `FORCE_CLOSED` before every line arrived, was never actually fully received and has no real cycle time to report; averaging per-supplier averages would incorrectly weight every supplier equally regardless of order volume (Decision Log, 2026-09-09 "Purchase Order Cycle-Time Report slice (OC-226)"). |
| BR-RPT-10 | Six of the seven reports reuse their underlying bounded context's existing view/manage permission; only the Dashboard gets a new dedicated permission. | A report that is just a different read-only presentation of data a user can already see elsewhere introduces no new capability or data exposure needing a new permission; the Dashboard uniquely aggregates across many separately-permissioned contexts that no single existing permission could correctly gate (Decision Log, 2026-09-08 "Inventory Dashboard slice"; 2026-09-09 report slices, each explicitly logging this same reasoning). |

## 4. Business Process / Workflow Narrative
Every screen in this sub-module is read-only and requires no user-driven process beyond navigating to it and, where offered, applying a filter (Stock Valuation's optional Location filter, Price Comparison's implicit per-product scope). A user opens the Inventory Dashboard for a cross-cutting "what needs attention" snapshot; opens Stock Valuation to see where stock value sits by category; opens PO Aging or PO Cycle-Time to assess how orders and suppliers are performing; opens Depreciation Summary to see the asset register's financial position by category; opens Price Comparison while sourcing a specific product, to see which supplier currently offers the best effective price; and opens Budget vs. Actual to see how committed spend compares to allocation by location. No report screen writes data, triggers a workflow, or feeds back into any other sub-module.

## 5. Success Criteria
Not formally defined with a numeric KPI. Inferred from feature completeness: `RELEASE_3_MILESTONES.md`'s R3-M7 row records 100% completion — "Inventory Dashboard, Stock Valuation Report, PO Aging Report, PO Cycle-Time Report, Asset Depreciation Summary, Price Comparison, and Budget vs. Actual all shipped (Cycle-Time was originally deferred as future work but was picked up as a follow-on in the same session)."

## 6. Assumptions & Constraints
- Assumes every report can remain a fixed, ERP-standard default shape (no custom filters/grouping/export) for this phase — a genuine report-builder capability is out of scope.
- Assumes live computation on every page load is acceptable — no deployment has yet surfaced a performance need for caching, snapshotting, or scheduled report generation.
- Assumes a single-currency, single-period-type reading of the data is acceptable where the underlying sub-modules themselves only weakly support multi-currency/multi-period (Budget vs. Actual, Price Comparison) — these limitations originate upstream (Procurement, Budget) and are only surfaced, not solved, here.

## 7. Known Gaps / Deferred
See SRS.md §6: no export on any report, no custom date-range/grouping controls, no scheduling/caching/historical snapshots, Budget vs. Actual's period-unaware summing across concurrent active budgets, Price Comparison's lack of currency conversion, and PO Cycle-Time's exclusion of `FORCE_CLOSED` orders from its average.
