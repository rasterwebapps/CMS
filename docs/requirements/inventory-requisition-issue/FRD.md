# Functional Requirements Document — Requisition & Issue

## 1. Overview
This sub-module implements the internal "draw already-on-hand stock" side of Inventory Management — Stock Indent (with its embedded Internal Return action), the per-location Reorder Configuration and nightly/on-demand Auto-Indent job that raises indents automatically, and the standalone Loanable Item Issue tracking record. It is the mirror image of the Procurement & Vendor Management sub-module's PR→PO chain, but for stock the organization already owns.

## 2. Actors & Permissions
All permissions are DB-managed rows (no hard-coded roles); the table below lists the exact codes found in the backend (`com.cms.inventory.indent`, `com.cms.inventory.issue`, `com.cms.inventory.stock`).

| Permission Code | Gates |
|---|---|
| `INVENTORY_REORDER_CONFIG_VIEW` / `_MANAGE` | Reorder Configuration CRUD + active/inactive status toggle |
| `INVENTORY_STOCK_INDENT_VIEW` / `_MANAGE` | Stock Indent CRUD, submit, cancel |
| `INVENTORY_STOCK_INDENT_APPROVE` | Department-head decision point (covers both approve and reject outcomes — one permission per decision point) |
| `INVENTORY_STOCK_INDENT_FULFILL` | Store decision point (covers all four outcomes: fulfill, fulfill-via-transfer, raise-PO, deny — one permission per decision point) |
| `INVENTORY_STOCK_INDENT_RETURN` | Internal Return action, separate from `_APPROVE`/`_FULFILL` — returning stock is a distinct, audit-worthy action from either decision |
| `INVENTORY_STOCK_INDENT_AUTO_RUN` | On-demand "Run Now" trigger for the Auto-Indent detection job, distinct from editing an individual indent (mirrors Wanted List's own `_RUN` permission) |
| `INVENTORY_LOAN_ISSUE_VIEW` / `_MANAGE` | Loanable Item Issue CRUD (create/issue) |
| `INVENTORY_LOAN_ISSUE_RETURN` | Mark-returned action, its own permission — a distinct, audit-worthy action from issuing |

Note: these permission codes are the result of an in-place rename (V532) from the original `INVENTORY_ISSUE_REQUEST_VIEW`/`_MANAGE`/`_APPROVE`/`_RETURN` — the same permission rows, carrying every existing role grant forward automatically, not new rows requiring a copy-forward migration. Every permission-seeding/renaming migration ends with the standing DEV_ADMIN/SUPPORT_ADMIN catch-all sync block; actual role assignment beyond that is done entirely in the DB-driven Role Management module.

## 3. Screens & UI Behavior
- **Reorder Configuration list/form** — filtered to `REQUESTING_POINT`/`BOTH` locations; real-time async pair-uniqueness check (`/pair-exists`) on (product, location), following the master-screen uniqueness pattern; a "drifted" warning tag ("On, no store set") shown when auto-indent is enabled but the location's default supplying location has since been unset; saving with auto-indent enabled is blocked at save time if no supplying store is set.
- **Stock Indents list/new/detail** — New form filters its requesting/issuing `<select>`s by `locationRole` via computed signals (`requestingLocations`/`issuingLocations`) so an invalid pair cannot even be picked, not just bounced by a backend 400. Detail screen surfaces, per line, the department-head decision (approve/reject with resolution notes) once `SUBMITTED`+`PENDING`, then the store's own four-outcome decision (fulfill/fulfill-via-transfer/raise-PO/deny) once `APPROVED`, each with its own audit trail (`resolvedBy`/`resolvedAt` vs. `storeDecidedBy`/`storeDecidedAt`, kept deliberately separate); a Fulfillment Context lookup (`/lines/{lineId}/fulfillment-context`) shows the issuing location's own stock, other locations' surplus, and any open PO as decision-support context before the store commits to an outcome. A `FULFILLED` line whose `sourceTransfer` is non-null displays as "fulfilled via transfer," distinguishing it from a direct issue with no separate status value. An `isAutoGenerated` badge/flag distinguishes system-raised indents from manually raised ones sharing the identical lifecycle.
- **Loanable Item Issues list/new + detail** — New form is a single-step Issue action (product restricted to `isLoanable = true`, borrower name required + optional contact, issue date, expected return date, optional deposit amount, optional condition-on-issue). Detail/list surface an "Overdue" indicator computed at read time (`expectedReturnDate` vs. today) and an "overdue only" list filter; Return is a single-step action (actual return date, condition-on-return) available only on an `ISSUED` record. Status badges: `ISSUED` and `RETURNED` both render via the shared `cms-status-badge` component's switch.

## 4. Functional Workflows

### 4.1 Stock Indent: create → submit → two-step per-line resolution
Create `DRAFT` indent against a requesting + issuing location pair (rejected at create time unless requesting is `REQUESTING_POINT`/`BOTH` and issuing is `STORE`/`BOTH`) → add lines (product, variant if the product has active variants, requested quantity) → **Submit** (`SUBMITTED`) → per line: **department-head decision** — `approveLine`/`rejectLine` on a `PENDING` line moves it to `APPROVED`/`REJECTED` with no stock consequence of its own (reversed from the original single-step design, see BR-RI-3) → **store decision** on an `APPROVED` line — exactly one of:
  - `fulfillLine` — posts an `ISSUE` movement (decrease-only) at the issuing location through `StockMovementService.recordMovement`, moves the line to `FULFILLED`;
  - `fulfillViaTransferLine` — first creates and completes a real `StockTransfer` from a chosen surplus location into the issuing location, then issues from the issuing location as above; the line's `sourceTransfer` FK records the transfer used;
  - `raisePoLine` — creates/links a `PurchaseRequisition`/`PurchaseRequisitionItem`, moves the line to `PO_RAISED` (terminal; the eventual restock is untracked back to this line);
  - `denyLine` — moves the line to `DENIED`, no stock consequence.
Header auto-completes (`COMPLETED`) once every line reaches a terminal state (`REJECTED`/`FULFILLED`/`PO_RAISED`/`DENIED`); `CANCELLED` reachable only from `DRAFT`.

### 4.2 Internal Return
On a `FULFILLED` line (i.e., actually issued), `returnLine` posts a `RETURN` movement with `direction: INCREASE` (widened from the original decrease-only `RETURN` handling shared with Return to Supplier, specifically for this use — see the GRN & Stock Control sub-module's own note on this shared enum value) at the issuing location, using the issuing location's own current weighted-average unit cost (fixed 2026-09-15; previously posted at zero cost, silently diluting the location's average). Accumulates into `returnedQty`, capped at `requestedQty − returnedQty` (service-layer check plus a DB check constraint `returned_qty <= requested_qty`).

### 4.3 Reorder Configuration → Auto-Indent detection
A reorder/catalog administrator sets `reorderLevel`/`reorderQty`/optional `maxStockQty`/`autoIndentEnabled` per (product, location) — enforced to `REQUESTING_POINT`/`BOTH` locations only, and blocked at save time if `autoIndentEnabled = true` with no `defaultSupplyingLocation` set on that location. `AutoIndentService.generate()` (cron `0 30 5 * * *`, or on-demand via `/auto-run`) reads every active, auto-indent-enabled config, nets `reorderLevel − (qtyOnHand + openIndentQty)` per (product, location) — where "open" excludes both `PENDING` and `APPROVED` lines (only genuinely terminal states reflect a real stock movement under the post-Phase-D meaning of `APPROVED`) — skips any product with active variants and any config whose location has since lost its supplying store, and bundles every shortfall for the same (requesting location, supplying store) pair into one new `StockIndent` with multiple lines, reusing `StockIndentService.create`/`addLine`/`submit` rather than new persistence logic.

### 4.4 Loanable Item Issue
`create` — validates the product is flagged `isLoanable`, records the loan as a standalone row with no Stock Ledger interaction, status `ISSUED`. `markReturned` — sets `actualReturnDate`/`conditionOnReturn`, status `RETURNED`. "Overdue" is a derived read-time flag/query predicate (`expectedReturnDate < today` and not yet `RETURNED`), never stored, needing no background job.

## 6. Data Model
See SRS.md §4.3 for the table list. Notable real-world column shapes confirmed directly from entity source:
- `ProductLocationReorderConfig`: `product`/`location` FKs, `reorderLevel`/`reorderQty` (`BigDecimal`, required), `maxStockQty` (nullable), `autoIndentEnabled`/`isActive` (`Boolean`), `createdAt`/`updatedAt` — at most one active config per (product, location) pair (partial unique index, V533).
- `StockIndent`: `requestingLocation`/`issuingLocation` FKs, `status` enum (`DRAFT`/`SUBMITTED`/`COMPLETED`/`CANCELLED`), `requestDate`, `notes`, `createdBy`/`createdAt`, `submittedBy`/`submittedAt`, `completedAt`, `updatedAt`, `isAutoGenerated` (`Boolean`, distinguishes `AutoIndentService`-created indents — same lifecycle either way).
- `StockIndentItem`: `stockIndent`/`product`/`variant` (nullable) FKs, `requestedQty`, `status` enum (`PENDING`/`APPROVED`/`REJECTED`/`FULFILLED`/`PO_RAISED`/`DENIED`), department-head audit trail (`resolvedBy`/`resolvedAt`/`resolutionNotes`), `returnedQty` (running total, default zero), store audit trail (`storeDecidedBy`/`storeDecidedAt`/`storeDecisionNotes`, deliberately separate from the department-head trail), `sourceTransfer` FK (nullable, set only on transfer-in fulfillment), `raisedRequisition`/`raisedRequisitionItem` FKs (nullable, set only on `PO_RAISED`).
- `LoanableItemIssue`: `product`/`location` FKs, `borrowerName` (required, plain text)/`borrowerContact` (nullable), `status` enum (`ISSUED`/`RETURNED`), `issueDate`/`expectedReturnDate`/`actualReturnDate` (nullable), `conditionOnIssue`/`conditionOnReturn` (nullable), `notes`, `issuedBy`/`issuedAt`, `returnedBy`/`returnedAt`, `updatedAt`.

## 7. Edge Cases & Validation Rules
- A Stock Indent whose requesting location is not `REQUESTING_POINT`/`BOTH`, or whose issuing location is not `STORE`/`BOTH`, is rejected at create time; the New form also filters both `<select>`s so an invalid pair cannot be chosen in the UI.
- A store fulfillment action on a line that is not currently `APPROVED` is rejected — a line must clear the department-head decision point before the store can act on it.
- An Internal Return exceeding `requestedQty − returnedQty` is rejected, enforced both in the service and via a DB check constraint.
- A Reorder Configuration cannot be saved with `autoIndentEnabled = true` and no `defaultSupplyingLocation` set on its location; the reverse (unsetting the store after the fact) is allowed and only surfaced as a drift warning, never blocked.
- Auto-Indent's netting query excludes both `PENDING` and `APPROVED` indent lines from "open" quantity (only genuinely terminal states reflect a real stock movement) — this changed meaning between Phase C (built when `APPROVED` still meant "issued") and Phase D (when `APPROVED` came to mean "awaiting the store"), and was corrected in the same Phase D change to avoid re-flagging every shortfall already sitting in a store's queue as a fresh shortage every night.
- A `SERIAL`/`BATCH`-tracked product cannot be added to a Stock Indent line or internally returned — the tracking-mode compliance check in `StockMovementService` fails since neither carries a batch/serial field end to end (known, unfixed cross-module gap).
- A Loanable Item Issue's product must be flagged `isLoanable`; creating one against a non-loanable product is rejected with a clear error.

## 8. Known Gaps / Deferred
See SRS.md §6 — no sourcing-preference automation for store fulfillment, Reorder Configuration/Auto-Indent skip variant-bearing products, batch/serial-tracked products cannot be indented or internally returned, no multi-tier auto-indent, and a Reorder Configuration's drift (auto-indent enabled, no supplying store) is surfaced as a warning rather than auto-corrected.
